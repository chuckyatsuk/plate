# Plate — a media service with a structural vault/delivery boundary

**Status: PROPOSAL.** Nothing here is built. This is the contract, written before
any code, so both sides can be generated from it rather than hand-maintained.
Per the repo's own doctrine: a proposal is not "true now" — the living docs win
until this is accepted and folded in.

Date: 2026-09-08 · Author: this planning session · Decisions by: chuck

---

## 1. What Plate is

**A service Files uses.** It holds files and serves renditions, with a hard
structural wall between the two. It knows nothing about works, exhibitions,
artists, galleries, or Vimeo.

That last sentence is the design constraint, not a nice-to-have. The moment
Plate knows what an artwork is, it stops being reusable and stops being worth
open-sourcing.

### The one-line version

> Plate stores originals that can never be served, and serves renditions that
> can never be oversized.

### Why it exists (from incidents, not aspiration)

Every property below traces to a real, dated failure in this project:

| Property | Incident |
|---|---|
| Vault objects have no delivery URL | Lightbox served `tr:orig-true`; a phone decoded 292MB in one bitmap, page peaked 516MB, tab died (2026-07-14) |
| Delivery routing in one place | `document` missing from the CDN bypass allowlist — every PDF hit the metered CDN, no error, only a bill (2026-09-08) |
| Metered paths are named | ImageKit auto-transcoded AV on first delivery; 16 "passthrough" loops burned the entire free video allowance, 528 units (2026-07) |
| Output megapixel clamp | Both providers 400 above ~25MP; Uri's shots run to 96MP |
| Decoded-memory clamp | iOS Safari counts decoded pixels, not file size; `navigator.deviceMemory` absent on Safari — the browser that actually dies |
| Unconditional faststart | HandBrake omits it; browser downloads the whole file before painting |
| One asset, derived renditions | A video today is FOUR Media docs a human relates by hand; miss one and the tile does not render at all |

## 2. Scope — deliberately thin

Research across ~45 services and projects (2026-09-08) established that the
image half of this problem is solved and the AV half is not. Plate therefore
**wraps existing engines** and owns only what does not exist elsewhere.

### Plate owns

1. **The vault/delivery boundary** — structural, not policy
2. **Intent resolution** — purpose in, URL out
3. **The decoded-memory clamp** — confirmed unoccupied across the industry
4. **The AV tier state machine** — including duration-ceiling refusal

### Plate delegates

| Concern | Engine | Why |
|---|---|---|
| Image transforms | **imgproxy** (Apache-2.0) | Already implements intent via `ONLY_PRESETS`, which *refuses* raw params. Mature, Go, actively maintained. Rewriting it is the naive move. |
| AV transcode/remux | **ffmpeg** | No credible alternative; PeerTube's invocation patterns are the reference |
| Document handling | **Gotenberg** (MIT) or **Tika** (Apache-2.0), if offloaded | Only if PDF work grows past passthrough |

> **Note:** imgproxy's video and PDF support is Pro-only ($49/mo). The AV leg
> gets built regardless — which is precisely where the strongest novelty sits.

### Explicitly NOT Plate

- External player references (Vimeo/SCHQ links + passwords) — **these live in
  Files.** They are editorial metadata about a work: Plate cannot verify,
  transform, meter, or delete them. Plate's job is to say *"no delivery
  rendition exists, and here is why"* so Files can render the right fallback.
- Any notion of artist, work, exhibition, catalogue, or rights.

## 3. The data model

### 3.1 Two tiers, structurally separated

```
Asset  (account-scoped, one per uploaded file)
 ├── Vault object      exactly one, immutable, NO delivery URL exists
 └── Renditions        zero or more, bounded, the only browser-reachable tier
```

**The invariant that makes this work:** a vault object and a rendition are
different types with different fields. A vault object has **no URL field at
all** — not a URL you are told not to use. Asking Plate for a vault object's
delivery URL is a type error, not a policy violation.

This is the structural version of "never hand `media.url` to an `<img>`."
The rule stops depending on human memory.

> **Prior art, worth copying exactly:** PeerTube's `VideoSource` is deliberately
> **not** a `VideoFile`, so a kept original structurally cannot enter the
> player's resolution set; its only route is a throttled, auth-gated download.
> This is the best implementation reference found. The negative example is
> Bunny, which serves `/{id}/original` and will hand a 1.4GB master to a phone.

**Every asset has exactly one vault original.** No exceptions — including when
the studio sends an already-web-safe 200MB H.264. In that case a rendition may
*point at* the vault object, after a verification pass (§5.3). One ingest path,
one invariant, easy to reason about.

### 3.2 Account scoping

**The account owns the files.** Artist is metadata on the asset, never a
container.

Uri has an account; his files are his. Sadie Coles has an account; her install
shots *of Uri's work* are hers — her photographer, her rights, her storage bill.
The same physical artwork legitimately has two assets in two accounts. That is
correct, not duplication to be deduped.

Consequences:
- Keys are `{account}/{asset-id}`. Plate never needs to know what an artist is.
- A gallery with 30 artists needs **no new container concept**.
- Cross-account sharing, if ever built, is an explicit grant — never implicit
  visibility.

### 3.3 Identity

Assets get **service-generated ids** (ULID or content hash). The human-readable
filename is **metadata, not identity**.

This removes the one piece of catalogue coupling in the current upload path:
`presign-upload/route.ts` today runs a Mongo query loop to dedupe filenames
before signing, because Payload's doc filename and the uploaded key must not
diverge. Plate owns key generation outright, and that loop disappears.

## 4. The delivery API

### 4.1 Intent, not transformation

```
GET /v1/assets/{id}/url?intent={intent}&device={class}
```

Callers name a **purpose**. They cannot pass width, quality, format, or crop.

| Intent | Media | Bound |
|---|---|---|
| `thumbnail` | image | small, admin/grid cells |
| `grid` | image | gallery tile |
| `lightbox` | image | clamped by BOTH megapixel wall and decoded budget |
| `poster` | video/audio | the still |
| `loop` | video | ≤30s, **silent**, ~640px — the grid tile |
| `detail` | video/audio | ≤12min, **with audio**, ≤1080p — the lightbox |
| `original` | any | **the only route to raw bytes, and it must be named** |

`intent=original` returns a short-lived, authenticated download URL — never a
CDN URL, never something embeddable. It is the explicit escape hatch, and
asking for it is a deliberate act.

**This is the whole reason to build Plate.** The CDN allowlist trap becomes
impossible: routing lives in one service that knows every type, rather than an
`afterRead` hook where a new `mediaType` silently falls through to a metered
CDN.

### 4.2 The decoded-memory budget — the industry gap

Confirmed unoccupied across 20+ image services, every DAM, every CMS, and every
AV service surveyed. The nearest artifact anywhere is one sentence in
Uploadcare's upload docs.

Two independent clamps, both applied:

```
clampWidthToOutputLimit   → guards the CDN   (~24MP; providers 400 above ~25MP)
clampWidthToMemoryBudget  → guards the TAB   (decoded RGBA bytes = w × h × 4)
```

24MP still decodes to ~92MB of RGBA. The first clamp does not save the phone.

**Device class must come from the client.** `deviceBudgetBytes()` reads
`navigator.deviceMemory` and `window.innerWidth` — inherently client-side. So
`device` is a request parameter; Plate does the math, the caller supplies the
input.

Critically: **`navigator.deviceMemory` is Chromium-only and absent on Safari,
which is the browser that actually dies.** A small viewport ALONE must be
sufficient to take the mobile budget. Never gate on `deviceMemory` being
present.

| Class | Per-image decoded ceiling |
|---|---|
| `mobile` | 24MB (~3 slides preloaded stays under ~72MB) |
| `desktop` | 96MB |

Default when unspecified: **`mobile`.** Fail toward the safe budget.

### 4.3 Honest refusal

When no rendition can exist, Plate says so in a form Files can act on:

```json
{
  "intent": "detail",
  "delivery": null,
  "reason": "exceeded_duration_ceiling",
  "detail": { "duration_s": 1_140, "ceiling_s": 720 }
}
```

This is the graceful-degradation fix for *"a video needs all three files or its
tile does not render at all."* Files decides what to show — a Vimeo embed, a
poster, a download link — because that is a product decision, not a media one.

Reason codes are a closed enum: `exceeded_duration_ceiling`,
`exceeded_size_ceiling`, `unsupported_format`, `pending`, `failed`.

## 5. Ingest and derivation

### 5.1 Broker uploads, own derivatives

| Flow | Model | Why |
|---|---|---|
| Upload | **Broker** — presigned PUT, browser writes direct to R2 | Plate never streams the bytes. Preserves the no-4.5MB-limit property the heavy-upload epic won; a 900MB video through a serverless request is where this falls over. |
| Derivatives | **Own** — Plate pulls from R2 with its own credentials | Server-to-server, needs to hold keys. Small blast radius: derivative worker only. |
| Delivery | **Neither** — Plate returns a URL string | Highest-traffic path stays cheap: metadata lookup + URL construction. |

**Accepted cost of brokering:** a browser that PUTs successfully then closes the
tab leaves an orphan object with no asset record. Requires a reconciliation
sweep (list bucket, find keys with no asset, clean up after N hours). This is a
scheduled job, not a hard problem, and it is cheaper than the alternative.

### 5.2 Three paths, three latencies

| Path | Mode | Notes |
|---|---|---|
| Vault ingest | **synchronous** | Presign, PUT, checksum, probe, record. Fast regardless of file size. |
| Image renditions | **synchronous / fast-queued** | Sub-second via imgproxy |
| AV renditions | **queued**, real job state | A 12-minute ProRes master is minutes of ffmpeg. Needs progress, retry, and failure that does not lose the vault object. |

**Because the vault write already succeeded, a failed derivative job is
recoverable rather than data loss.** Re-run it. Today a partially-completed
video ingest leaves a tile that will not render.

### 5.3 Verification on ingest — fail closed

Plate probes vault objects and records true dimensions, duration, codec, and
container, and **refuses to promote** to delivery anything that breaches a
ceiling.

This generalises the existing AV-delivery guard (`Media.ts:452`), which rejects
an upload rather than serving it expensively — the pattern is already house
style.

> **Refinement (2026-09-09, from Phase-2 build review): fail-closed does not mean
> synchronous.** "Fail closed" means the vault never accepts an object it cannot
> *account for* — existence and identity, confirmed synchronously at finalize (a
> HEAD proves the object landed; size comes from storage; the checksum is verified
> against the stored object, never taken on the client's word). It does **not**
> require every *delivery property* to be known synchronously. Probing for
> delivery properties happens where the media runtime lives:
>
> - **Images** are probed in the API at finalize — but header-only, via a ranged
>   GET of the first ~64KB, never a full download (a 300MP TIFF is ~300MB).
> - **A/V** is **not** probed in the API. The API is deliberately probe-less (no
>   ffprobe; §Q4 keeps the fat media runtime on the worker), and pulling a
>   multi-GB master into a sub-100ms request is the exact "900MB through a
>   serverless request" failure the §5.1 broker exists to avoid. Instead finalize
>   creates the asset `probe_status: pending` and enqueues the worker, which
>   probes as its first step, backfills the vault metadata, and enforces the
>   duration ceiling on the **measured** duration. A ceiling breach writes a
>   `failed` rendition with a closed-enum reason; delivery then returns
>   `delivery: null` + that reason (§4.3). A genuinely unprobeable object marks
>   the asset `probe_status: failed`.
>
> This is consistent with the rule that **refusal is a delivery concern, not a
> storage one** — the vault takes the bytes; delivery decides what can be served.

### 5.4 Ceilings — configuration, not constants

| Rendition | Ceiling | Source |
|---|---|---|
| image output | ~24MP | both CDNs 400 above ~25MP (measured 2026-07-12) |
| decoded (mobile) | 24MB | iOS per-tab reality |
| decoded (desktop) | 96MB | |
| `loop` | ≤30s, silent, ~640px | grid tile |
| `detail` | **≤12 min**, audio, ≤1080p | chuck 2026-09-08 |

Every one is an env var (`PLATE_MAX_DELIVERY_DURATION=720s`). A public repo
needs them adjustable, and real galleries will want them tuned.

**On the 12-minute figure:** an earlier draft proposed 3 minutes, anchored on
the Madre excerpts (28s–1m34s) — which were excerpts precisely because someone
had already cut them down. Video art routinely runs longer. At 12 minutes the
ceiling is a rare fallback rather than a routine gate, which is the right shape.
Note this also rules out **Cloudflare Media Transformations** as an engine: its
100MB / 10-minute input ceiling sits below both this ceiling and the actual
Madre masters (39MB–1.4GB).

### 5.5 Faststart, unconditionally

`-movflags +faststart` at the **preset layer** AND on the **stream-copy path**,
so remux-only passes are progressive-safe. **No config switch to forget.**

This is PeerTube's pattern, and the reason to copy it structurally rather than
document it:

- HandBrake omits faststart by default (this project's landmine)
- **AWS MediaConvert defaults `Mp4Settings.MoovPlacement` to `NORMAL`** — the
  same trap at the API level, from a first-party AWS service
- FFmpeg's own docs confirm it is not enabled by default
- Because originals serve from R2, **no vendor takes this off your hands** —
  Mux, Cloudflare, Bunny, api.video and Transloadit all leave it undocumented,
  because they never touch your container

## 6. The contract

**A `contract/` directory, with both sides generated from it.** OpenAPI or
protobuf — the format matters less than the generation.

This is non-negotiable for one reason: this project's documented recurring bug
class is *"something looks configured, but the real data path goes elsewhere."*
Adding a network boundary **multiplies** that risk unless the contract is
generated rather than hand-maintained. Every drift becomes a compile error
instead of a 200 that is wrong.

## 7. The test suite is the actual asset

**Port the incidents as tests before writing the service.** Each has a date and
a real failure behind it:

```
28MP input returns a clamped rendition, never a 400
a document/PDF never routes to ImageKit
a mobile-budget lightbox rendition never exceeds 24MB decoded
deviceMemory absent (Safari) + small viewport → mobile budget
every generated MP4 has moov before mdat (ffprobe the artifact, not the flag)
a vault object exposes no delivery URL, at any intent but `original`
a 13-minute video refuses `detail` with exceeded_duration_ceiling
a new media type added without an allowlist entry FAILS, loudly
```

Two properties of this suite:

1. **It solves the ephemeral-database problem for the media layer.** No Atlas,
   no live shared DB, no hand-run scripts. `go test`, in CI, on every commit.
   That is the root cause identified at the start of this session, resolved for
   the part of the system where it hurt most.
2. **It is the credible portfolio artifact.** Every test has an incident behind
   it. That reads as field experience, not exercise.

**Verify the artifact, not the flag** — house rule. `ffprobe` the output;
do not assert that the option was passed.

## 9. Consequences for Files

- **A video stops being four documents.** Today `posterImage`, `previewLoop`,
  `detailVideo` are separate Media docs a human uploads and relates by hand;
  miss one and the tile does not render. In Plate: one asset, derived
  renditions, requested by intent.
- **~1,700 lines of field components shrink.** `MediaRef`/`MediaArray`/
  `MediaList`/`WorksPicker` exist largely to resolve bare relationship IDs over
  REST and build thumbnails. Two known bugs die with them: `MediaList` has no
  chunking against `limit=100` (a work with >100 images silently loses
  thumbnails) and no `mediaType` gate (a video gets an *image* transform).
- **ImageKit becomes optional.** If imgproxy handles image transforms,
  self-hosting replaces a metered vendor — and the ImageKit Free 2-origin cap
  stops being a blocker on new instances. Not decided here; the spec must not
  assume ImageKit stays.
- **Local dev gets harder** — two processes. Budget a `docker-compose` or
  `make dev`, which this repo has never had.

## 10. Decisions and open questions

### Q1 — Contract format: **OpenAPI 3.1** ✅ (2026-09-08)

Not protobuf. Reasons, in weight order:

- **Open-source adoption.** A stranger can `curl` an OpenAPI service and see it
  work in ten seconds; gRPC means installing tooling first. For an audience of
  "people trying to do more independently," this is decisive.
- **The caller is a browser-adjacent TS app.** gRPC-Web needs a proxy in the
  deployment for the sole benefit of talking to one service.
- **Plate's core verb is `GET a URL`** — request/response returning a string,
  wanting HTTP caching. Protobuf's strengths (streaming, high-frequency RPC)
  are unused; reaching for the heavier tool without a reason reads as *worse*
  judgment, not better.
- **imgproxy is HTTP.** A second protocol at our own boundary buys nothing.

**The discipline this costs us:** OpenAPI is easy to be sloppy with. Closed
enums for `intent` and `reason`, required fields marked required, no bare
`object`, `additionalProperties: false`. Generated clients both sides
(`oapi-codegen` for Go, `openapi-typescript` for Files) — the format matters
less than the generation.

Revisit only if Plate grows a high-frequency internal API; job progress is fine
as SSE or polling, and gRPC could be added alongside rather than instead.

### Q2 — Datastore: **Plate owns its own Postgres** ✅ (2026-09-08)

The test: *can Plate answer its own questions without asking Files?* If not, it
is a library with network latency, not a service.

| Plate owns | Files owns |
|---|---|
| Asset id, account, vault key, checksum, size | Which work an asset depicts |
| Probed metadata (w/h, duration, codec, container) | Caption, credit, display intent |
| Renditions: intent, key, dimensions, status | Ordering in a gallery |
| Job state: queued/running/failed, retries | The Vimeo/SCHQ link + password |
| Refusal reasons, grants (§Q3) | Everything domain-shaped |

Files stores a **Plate asset id** and nothing else about the file. `Media`
shrinks from carrying `width`/`height`/`cloudinaryPublicId`/`posterImage`/
`previewLoop`/`detailVideo` to a domain object pointing at an asset.

**Why it matters beyond tidiness:** a service that borrows its caller's database
cannot be extracted, open-sourced, or adopted by a stranger. It also makes Plate
independently testable against an ephemeral Postgres container — which is the
root-cause fix for this repo's "every behavioural check needs the live shared
DB" problem.

**Accepted costs:** two sources of truth for existence (reconciliation sweep —
needed anyway for brokered-upload orphans, §5.1); deletion becomes async
two-step (Files marks intent, Plate reconciles — no distributed transactions);
a second database to operate.

**Rejected:** stateless Plate with all state in Files. Fails immediately on the
AV path — a queued transcode needs durable state surviving restart, and it
cannot live in the caller's schema without Plate having write access to it.
That is not a boundary.

**Accounts are a first-class table** (id + storage config: bucket, prefix,
delivery endpoint, quotas). This is what lets ONE Plate deployment serve Uri,
the demo, and a future gallery without env-var-per-instance gymnastics — the
fleet problem dissolves rather than moves.

> ⚠️ **Keep Plate's account an opaque foreign reference** — an id plus storage
> config, with NO users, roles, or permissions. Identity is a separate concern
> and a future shared service. If Plate invents its own user model it will have
> to be fought later. This is the premature-entanglement trap that produces the
> frankenstein (§14).

### Q3 — Auth: **three problems, three answers** ✅ (2026-09-08)

Conflating these is the classic media-service security failure.

#### A. Service-to-service — scoped JWT

Files→Plate carries a signed token with `account`, `scope`
(`assets:read` / `assets:write` / `renditions:generate`), short expiry.

> **The critical rule: the account is a CLAIM, never a request parameter.**
> Plate checks `token.account == asset.account`. If Files instead passed
> `?account=X`, the caller would be asserting its own identity — which is how
> cross-tenant leaks happen. This makes account isolation structural, the same
> principle as the vault/delivery wall.

*Rejected:* shared API key (no structure, no scoping, rotation = downtime);
mTLS (authenticates the client, not the request — still needs authz on top;
hostile to self-hosters. Composes fine with tokens later on K8s).

#### B. Delivery — three modes, chosen per asset

| Mode | Use | Mechanism | Cost |
|---|---|---|---|
| **Public** | artwork on a public page | stable unsigned URL | none, fully CDN-cached |
| **Signed** | admin/preview, revocation not the point | stateless signature, short expiry | none, coarse-expiry caching |
| **Granted** | share links, packages, consignments | **real token state, DB lookup per request** | uncacheable, Plate in the hot path |

Only `granted` pays the cost, and only where revocation is the product.

#### C. Direct upload — narrowly-scoped presigned PUT

Bounded on exact key, content-type, content-length range. Expiry generous
enough for a studio's slow connection (the current hour, learned the hard way —
a few-hundred-MB file at ~1–2 Mbps blows past 600s and R2 rejects mid-stream).
The browser must be able to write **only** that one object.

#### Grants are first-class objects

A grant is a record: *"this link can see these files, until this date."*
Not a token attached to a URL — an entity.

```
Grant
  id, account, subject (the SET it covers), recipient (optional),
  created, expires, revoked_at, access_log
```

**One grant per SET (package/share link) — never per file** (chuck
2026-09-08). Per-file grants spiral: 40 packages × 40 works = 1,600 rows to
revoke and reason about individually. One row, one decision, one revocation.
This matches how Packages already work — **Send freezes a snapshot**, so the set
is defined at issue time and does not drift. Adding a work later is a new
version and a new grant, which is the honest behaviour anyway.

What state buys, and why it is worth the lookup:

- **Revoke** — every image in the package stops loading, everywhere it was
  forwarded. Today a copied image URL works forever, for anyone, with no record.
- **Observe** — "opened 14 times, last Tuesday." The question dealers ask
  constantly, and one of Artlogic's stickier features.
- **Expire by itself** — consignment ends in December, access ends in December.

> **The coherence worth building toward: access follows custody.** The ledger
> already answers *who has what right now*; a grant answers *who can SEE what
> right now*. Same fact, applied to files. When a consignment ends the grant
> ends — nobody has to remember. Artlogic cannot do this because their file
> sharing and inventory model are separate systems.

**Plate holds the grant; Files owns WHY it exists.** Plate knows "grant G
permits account A's set S until D." Files knows "because package P was sent to
a gallery on the 14th." Same discipline as the Vimeo decision.

#### OAuth-shaped, not OAuth-implemented

No OAuth server now — there is one client. But use standard JWT claims (`iss`,
`sub`, `aud`, `exp`, `scope`), treat scopes as first-class from day one, and
keep token *issuance* separable from *validation*. Then adding an authorization
server later means swapping the issuer, not rewriting Plate. The third-party
integration case (a gallery's own tooling, an assistant with limited access) is
foreseeable but not yet real.

#### Explicit performance trade

A grant check per tile means a 197-tile page is 197 lookups per visitor.
Mitigation is a short-TTL in-process cache keyed by grant id, which makes
**revocation eventually-consistent — effective within seconds, not instantly.**
Decide this now: retrofitting it after a slow page is messy. And note the
reliability shift — with grants, Plate is in the request path, so if Plate is
down, gated images do not load (a stateless signed URL keeps working).

### Q4 — Runtime: **containers on Hetzner, API and worker split** ✅ (2026-09-08)

#### Plate is TWO processes, not one

This matters more than the hosting choice. Same binary, different commands
(`plate serve` / `plate work`), split from day one:

| | Profile | Requirement |
|---|---|---|
| **API** | sub-100ms, spiky, scales with page views | High availability — with grants, gated images do not load if it is down |
| **Worker** | minutes of CPU, memory-hungry, scratch disk | Retryable; nobody is waiting on the request |

Deploying them as one thing means either the API inherits the worker's fat
runtime or the worker inherits the API's timeouts.

#### Serverless is out for the WORKER — but the API would fit Vercel fine

Worth stating so it is not re-litigated: **Fluid Compute is a genuinely good fit
for the API half** — spiky, sub-100ms, stateless, scales to zero. Grant lookups
and URL construction are exactly that shape. A split deployment (API on Vercel,
worker on Hetzner, both against Supabase) is legitimate and cheaper on the API
side.

Rejected in favour of both-on-Hetzner for three reasons: one box already paid
for runs both, so splitting saves nothing and adds a deploy target; **the compose
file IS the open-source quickstart**, so production and self-hosting stay the
same artifact; and API and worker are the same binary with different commands —
splitting hosts means two pipelines for one program.

> The general trap, and the reason this is written down: let the workload pick
> the platform, not the platform pick the architecture. "We are on Vercel" is
> roughly how the media pipeline ended up spread across an `afterRead` hook,
> four field components and a landmine list.

#### Serverless is out for the worker

Concretely: Vercel functions cap at **300s** and a 12-minute ProRes transcode
exceeds it; ffmpeg needs real scratch disk; wall-clock billing on a CPU-bound
job is the worst possible pricing shape; cold starts with a fat ffmpeg image are
brutal. Fluid Compute is genuinely good for the *API* shape — nothing fixes "this
job runs for twenty minutes."

#### The stack

```
docker compose up
├── plate-api      Go, stateless, horizontally scalable
├── plate-worker   Go + ffmpeg, 1..N, scales with queue depth
├── postgres       asset / rendition / grant state
└── imgproxy       image transforms, ONLY_PRESETS
```

Start with one box running all four. When ingest load justifies it, the worker
moves to its own node against the same Postgres — **no code change**, because
the queue is already the coordination point.

#### Hosting: **Fly.io now, host-agnostic by design** ✅ RESOLVED (2026-09-09, chuck)

> **This supersedes the two conflicting "final" blocks that follow.** An earlier

#### Comparison A — Cloud Run Jobs (worker) + Vercel (API)

Revised after reading Google's published pricing. **No server to be
responsible for, and the worker is free at this volume.**

**Cloud Run Jobs free tier: 240,000 vCPU-seconds + 450,000 GiB-seconds/month —
that is 66 vCPU-HOURS free every month.** Estimated transcode load for ~50
videos is ~25 vCPU-hours, so it sits **entirely inside the free tier**. Google's
own Example 5 (a job run 730×/month, 1 min each) totals **$0.00**. Paid rate
beyond it is $0.000018/vCPU-second — cheaper than Fly's `performance-2x`.

| | Idle | ~50 videos/mo | Back catalogue (~200) |
|---|---|---|---|
| **Cloud Run Jobs** | **$0** | **$0** (free tier) | **~$0–3** |
| Fly.io | ~$0.30 | ~$3 | ~$9 |
| Hetzner CCX13 | $50 | $50 | $50 |

**The API goes on Vercel, not Cloud Run.** Already paid for (Pro), right shape
(spiky, sub-100ms, stateless). Cloud Run *services* bill differently from jobs —
$0.000024/vCPU-second of active time — and Google's Example 2 (CPU-bound,
one request per instance, 10M requests) lands at **$81/mo**. Plate's API is much
lighter than that example, but Vercel is simpler and already sunk cost.

**Final stack:** API → Vercel · Worker → Cloud Run Jobs · Postgres → Supabase
($10 marginal) · Storage → R2. **All-in ≈ $10/mo**, essentially just Supabase.

⚠️ **Region: use TIER 1** — `europe-north1` (Finland) or `europe-west1`
(Belgium), both well-placed for a Supabase EU region. Avoid Tier 2
(`europe-west3` Frankfurt, `europe-west2` London) — same service, higher price.

⚠️ **Cloud Build and Artifact Registry bill separately** and are NOT in the
Cloud Run tables. Artifact Registry has a free tier a fat ffmpeg image could

Accepted tradeoff: a split deployment across two platforms, and some GCP setup.
At $0 vs ~$3/mo for the worker with the API already covered, it wins anyway.

#### Comparison B — Fly.io (revised 2026-09-08, against real pricing)

**Fly.io over a Hetzner box** — and no server to be responsible for. (This is the
option chosen for now; see the RESOLVED banner above.)

The workload is **bursty ingest, idle most of the time**. Per-second billing
with scale-to-zero fits that; a fixed box does not. Against Fly's published

| Scenario | Cost/mo |
|---|---|
| Idle (stopped-machine rootfs only, ~2GB @ $0.15/GB) | **~$0.30** |
| Light (~10 videos) | ~$1 |
| Steady (~50 videos) | ~$3 |
| Back-catalogue burst (~200 videos, one-off) | ~$9 |

Worker sizing: **`performance-2x`** (2 perf CPU / 4GB, $0.0861/hr). A 12-min
source ≈ 30 min compute; 50 videos ≈ 25 hrs ≈ $2.15.

> ⚠️ **Use `performance`, never `shared`.** Shared CPUs are throttled and ffmpeg
> would crawl — wiping out the saving and blowing the duration ceilings.

Egress is ~zero because **Plate returns URLs and R2 serves the bytes** (Q5) —
that decision pays off directly here. Scratch disk: prefer ephemeral machine
storage over a Fly Volume ($0.15/GB/mo, billed attached or not).

**All-in ≈ $10–20/mo** (mostly the $10 Supabase marginal), vs **~$50/mo** for a
CCX13 idling. Verified pricing 2026-09-08.

⚠️ **Watch for orphaned resources** — Fly's Managed Postgres survives app
deletion, and volumes bill whether attached or not.

#### Rejected: a Hetzner box (for now)

A CCX13 is ~$50/mo (~$600/yr) — a real line item for a project with no revenue.
It only wins if **other projects consolidate onto it**, which is a separate
stack-audit question (chuck flagged 2026-09-08: Hetzner + ImageKit + Supabase +

**This is reversible either way** — it is the same container. Moving to a box

#### Earlier reasoning, kept for the box option

CPU-heavy, bandwidth-light, predictable cost — a dedicated-vCPU CCX box
(~€25–50/mo) transcodes comfortably, and the account already exists.
*Digital Ocean:* ~1.5–2× the cost for equivalent compute; fine if the polish is
worth it. *Cloudways:* ruled out — a managed layer priced for PHP/WordPress
agencies, charging a premium for management irrelevant to containers while
giving less control over the one thing that matters (CPU for transcoding).

#### Managed Postgres: **Supabase, from day one** (revised 2026-09-08)

chuck already pays for Supabase on other projects — **marginal cost ~$10/mo**.
That is cheap enough to skip the self-run stage entirely:

- no "migrate local Postgres → managed" task ever gets written
- backups + PITR + failover from the first row, which matters as soon as a
  client's asset metadata lives in it
- the compose file gets *simpler* — three containers, not four
- it absorbs the operational half most likely to bite badly

Local dev still uses a throwaway Postgres container; only deployed environments
point at Supabase. **The shipped compose file must still include a Postgres
container** so a stranger gets `docker compose up` and it works — Supabase is
our production choice, never a requirement baked into the project.

> ⚠️ **Co-locate the regions.** Grant lookups are in the hot path for gated
> images. A Hetzner box in Germany against a US Supabase region puts the
> Atlantic in every tile request. Verify before committing, not after.

#### Cost (2026-09-08)

| Item | Monthly |
|---|---|
| Hetzner CCX (dedicated vCPU) | €25–50 (~$30–55) |
| Supabase (marginal — already paid for) | +$10 |
| R2 storage | ~$1.50 / 100GB, zero egress |

Against that: **Mongo Atlas (~$8) eventually retires** with the Postgres
migration, and ImageKit's future $9–89/mo never arrives (its Free 2-origin cap
is currently a hard blocker at instance #3). **Steady-state net: ~$35–60/mo.**

**The real cost is not the money** — it is the first server chuck has to patch,
monitor and be on call for. Supabase absorbs the database half of that.

#### The queue: Postgres, `SELECT … FOR UPDATE SKIP LOCKED`

No Redis, no RabbitMQ, no SQS. Postgres is already there, it is **transactional
with the asset state** (a job and its rendition row commit together — no "job
succeeded but the record didn't update"), and `SKIP LOCKED` is genuinely good at
this. Redis would buy throughput unreachable at any plausible scale for this
workload, in exchange for another service every self-hoster must run.

#### Kubernetes: **no** (chuck 2026-09-08)

Right answer at scale, wrong for four containers and a handful of transcodes a
day — real ongoing overhead, operated alone, for no operational return. It also
narrows the open-source audience to cluster operators, which is the opposite of
"artists and small institutions doing more independently."

**But build K8s-READY, because it costs nothing and is just twelve-factor
discipline:** config purely from env, no local state in the API, health +
readiness endpoints, structured logs to stdout, graceful SIGTERM shutdown, and a
worker that survives being killed mid-job (idempotent and retryable — required
anyway). Then `deploy/k8s/` manifests are a thin optional addition for an
institution that wants them.

> Note for the CV question this touches: deploying a low-traffic service on K8s
> teaches `kubectl apply`, not the operational depth (OOMKills, stalled
> rollouts, network policy, StatefulSets) that is actually valued. Get that
> deliberately — k3s/kind locally, or the CKA — not by inflicting a cluster on a
> project that does not need one.

#### Multi-client: an accounts row, not an architecture change

Plate is already multi-account (Q2). What grows with client count:

| Resource | Scales with | Whose problem |
|---|---|---|
| Storage | client count, linear | R2's |
| Delivery bandwidth | page views | R2/imgproxy's |
| Grant lookups | page views | small indexed reads, cached |
| **Transcode CPU** | **ingest events, not client count** | **ours — the only real one** |

Transcoding is **bursty and correlated with onboarding**, not steady-state use.
A gallery uploading its back catalogue is a spike; six months later it is idle.
So size for **worst-case concurrent ingest** and keep the worker horizontally
scalable — a spike is "run three workers for two days," not "buy a bigger box
forever."

**Clients SHARE one deployment.** Per-client deployments would recreate exactly
the fleet-provisioning burden this is escaping. A confidentiality-sensitive
client can be peeled onto a separate deployment later; preserving that escape
valve costs nothing.

> ⚠️ **The isolation model changes here, and this is the real multi-client
> work.** Files gets isolation *structurally* — one process, one DB, one bucket,
> no code path can name another artist's data. Plate deliberately trades that
> for one deployment with many accounts, which means **isolation is enforced by
> CODE, not architecture.** The Q3 rule (account is a token claim, never a
> request parameter) now carries the weight separate deployments used to carry.
> It requires: a test that account A's token cannot read account B's asset **at
> every endpoint**, per-account bucket/key prefixes, and that test in CI — the
> way `smoke-negative-access` is today.

### Q5 — Storage and the byte path ✅ (2026-09-08)

**Storage is R2**, both tiers. Vault originals and generated renditions both
live in R2; Plate's Postgres holds only *metadata about* them (keys, checksums,
probed dimensions, status, grants). S3-compatible, so a self-hoster points it at
any S3.

**Plate serves URLs, never bytes** (chuck 2026-09-08). For public and signed
modes Plate is never in the byte path — it returns a URL and R2/imgproxy serve
it.

> **The honest gap this leaves:** for `granted` content Plate checks the grant
> and then hands back a URL — which keeps working until it expires. So
> revocation is **not instant**, and a URL copied out of the page resolves for
> its remaining lifetime.
>
> **Mitigation: short expiry on granted content — minutes, not hours.**
> Revocation is then effective within one expiry window, which satisfies every
> realistic gallery use case ("the link stops working within 5 minutes").
>
> The airtight alternative is Plate **proxying** bytes for granted content, so
> no leakable URL exists at all. Rejected for now: it puts bandwidth and
> availability in the image-loading path. It stays available later for a client
> who genuinely needs it, and it is an **additive** change, not a rewrite.

**ImageKit's future:** with imgproxy handling transforms, ImageKit becomes
optional — which also removes the Free-plan 2-origin cap as a blocker on new
instances. Not decided here; the design assumes nothing about ImageKit staying.

## 10b. Why this shape — the frankenstein problem

*(chuck, 2026-09-08. Recorded here because it is the reasoning behind every
decision above, and the thing a later reader will most need.)*

**The direction of travel: a mature successor to something like Artlogic.** Not
full-feature from day one — but foundations that stay scalable when the
experience branches into several services, rather than one process choking on
everything.

That is the road this project was already on. Files was accreting inventory,
ledger, finance, packages, CRM, website rendering, media pipeline and exports
into one Payload process against one Mongo database. **Each addition was
individually reasonable. The aggregate was heading somewhere nothing could be
changed independently.**

So the useful reframe: **Plate is not an extraction, it is the precedent that
services get extracted at all.** It is the first and the one whose boundary is
most obvious. If it works, the same reasoning applies later to the ledger, to
packages/sharing, to rendering.

Three principles, cheap to write down now and expensive to retrofit:

1. **A service owns its data or it is not a service** (Q2). The moment two
   services share a database you have a distributed monolith — worse than a
   monolith. This single rule is what prevents the frankenstein.
2. **Domain-free services are the reusable ones.** Plate knows nothing about
   artworks; that is why it is open-sourceable, testable and replaceable. The
   services that *do* encode domain (ledger, custody, consignment) are the
   actual product — and should stay thin, because they are hardest to change.
3. **Contracts before implementations** (Q1). A generated contract is what lets
   a service be replaced later without archaeology.

**Corollary for Payload/Mongo:** the eventual move is probably *not* "replace
Payload." Payload is a legitimate service for editorial content and page
rendering; it is a bad *platform* for inventory, ledger and finance. The
migration is "stop asking Payload to be the whole system," which is far less
dramatic and may leave Payload alive in a narrower role.

## 13. Open-sourcing

Public repo on chuck's personal GitHub, referenced from `everysinglefile.com`;
Plate's README references Files as its first consumer.

**Framing matters.** "I built an image CDN" reads naive — that space is solved.
The accurate framing is synthesis:

> OAIS preservation/access separation enforced **structurally** rather than by
> policy, with intent-based delivery extended to A/V and a decoded-memory-aware
> clamp.

The security framing is stronger than the ergonomic one: Rails shipped named
variants and then CVE-2026-66066 (CVSS 9.5, arbitrary file read via libvips).
**Intent APIs are attack-surface reduction**, not just tidiness.

**Scrub client specifics.** Port the technical facts (28MP 400s, HandBrake omits
faststart, iOS counts decoded pixels); drop the client-identifying narrative.
The knowledge is the value; a named studio's outage does not belong in a public
repo.

> ⚠️ **Do not overclaim novelty.** The vault/delivery split IS OAIS AIP/DIP —
> decades old and familiar to every archivist. Claiming the architecture as a
> whole is new "wouldn't survive contact with anyone who knows the archival
> field," and would alienate exactly the audience most likely to value this.
> What is genuinely unoccupied is narrower and worth stating precisely:
> **structural** rather than policy enforcement of that split, the
> decoded-memory clamp, and purpose-tiered AV. Claim those three; cite the
> lineage for the rest.

### What the research established (2026-09-08, ~45 projects surveyed)

- **Vault + intent combined: nobody.** The concept is ancient (OAIS AIP/DIP,
  preservation master vs access copy) but enforcement is ACL-by-policy
  everywhere. Directus built the best intent-preset lockdown and *explicitly
  declined* to gate the original. A Hyrax issue asking for this has been open
  **nine years**. PeerTube is the closest structural implementation — video
  only.
- **Decoded-memory budget: unoccupied.** No counterpart found anywhere.
- **Purpose-tiered AV: unoccupied.** Every "ladder" in the industry is an **ABR
  bitrate ladder** — same content, same duration, same audio, varying quality
  for network adaptation. Duration-and-audio-by-purpose is orthogonal.
  Mux's animated previews are silent because GIF/WebP *cannot carry audio* — a
  format side-effect, not a modeled decision. PeerTube's plugin contract carries
  resolution, fps, bitrate, and **no duration field and no purpose enum**.
- **Full mixed-media in one self-hostable service:** only Nextcloud — and its
  `Movie`/`MP3`/`PDF` providers are **disabled by default**, which is this
  project's exact bug class.
